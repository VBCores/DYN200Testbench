# DYN-200 через libcxxcanard и DSDL

Эта памятка описывает обмен со стендом без API из `include/voltbro_testbench_client/`. Примеры используют libcxxcanard и сгенерированный DSDL-тип `uavcan.primitive.scalar.Real32.1.0`.

## Подключения

| SocketCAN | Устройство | Известные Cyphal node ID |
| --- | --- | --- |
| `vcan2.0` | Контроллер стенда DYN-200, включая тормоз | Обычно `79` |
| `vcan1.0` | Отдельная моторная линия VBDRIVE по новой схеме | На прежней линии наблюдался ID `4`; после переноса проверьте фактический ID |

В этой конфигурации возможны также моторные линии `vcan3.0`–`vcan6.0`. Имена интерфейсов создаёт мост ethernet-can; приложение использует уже созданные Linux SocketCAN-интерфейсы. Настройки CAN FD стенда: nominal 1 Мбит/с, data 8 Мбит/с.

Локальный node ID компьютера в примерах — `101`. На выбранной CAN-линии этот ID должен быть свободен. ID источника стенда в сообщениях проверяется как `79`. Моторный узел отдельный: не переносите на него ID стенда.

Оба бинарных примера используют локальный ID `101`. Не запускайте их одновременно на `vcan2.0`, пока не измените ID одного из них на другой свободный адрес: две программы с одинаковым node ID будут конфликтовать.

## DSDL-тип и заголовки

Оба примера используют один тип: `uavcan.primitive.scalar.Real32.1.0`. Для C++ это `uavcan_primitive_scalar_Real32_1_0`, объявленный сгенерированным заголовком:

```cpp
#include <uavcan/primitive/scalar/Real32_1_0.hpp>
```

Для этого заголовка нужны каталоги сгенерированных DSDL-файлов `generated/cpp` и `generated/c`. Для API транспорта нужны include-каталоги libcxxcanard и `libcxxcanard/libs`. В клиентские заголовки `voltbro_testbench_client` включать ничего не требуется.

В репозитории уже есть минимальные цели CMake, напрямую линкуемые с `libcxxcanard`:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target read_dyn200_raw send_brake_5103 -j
```

Если libcxxcanard уже находится локально, передайте его каталог при конфигурации:

```bash
cmake -S . -B build -DVTC_LIBCXXCANARD_SOURCE_DIR=/path/to/libcxxcanard
```

## Subject ID стенда

| Subject | Направление | DSDL | Значение |
| --- | --- | --- | --- |
| `5100` | DYN-200 → слушатель | `Real32` | Скорость, об/мин |
| `5101` | DYN-200 → слушатель | `Real32` | Момент, Н·м |
| `5103` | отправитель → DYN-200 | `Real32` | Команда тормоза от `0.0` до `1.0` |

Скорость и момент — отдельные публикации, не синхронная пара. У каждого subject собственный Transfer-ID; общего номера пробы или времени измерения в сообщениях нет. В текущем режиме поток может доходить примерно до 1 кГц на каждый канал.

Для чтения подпишитесь на subjects `5100` и `5101`, декодируйте `Real32` и обрабатывайте входящие сообщения в `bus->loop()`. Отбрасывайте сообщения, если `transfer->metadata.remote_node_id` не равен ID стенда. Полный пример: [`read_dyn200_raw.cpp`](../examples/read_dyn200_raw.cpp).

Для отправки тормоза создайте `Real32`, задайте `value`, затем вызовите `bus->send_msg(&command, 5103, &transfer_id)`. Инициализируйте отдельный Transfer-ID для subject; `send_msg` обновляет переданный счётчик при отправке. Пример использует API библиотеки напрямую и выталкивает очередь TX через `process_tx_once()`. Он сразу отправляет `0`, затем чередует `0.5` и `0` с интервалом в секунду. Полный пример: [`send_brake_5103.cpp`](../examples/send_brake_5103.cpp).

Запуск чтения:

```bash
./build/read_dyn200_raw
```

Отправка `5103` физически меняет сигнал тормоза:

```bash
./build/send_brake_5103
```

Контроллер принимает значения от `0.0` до `1.0`, отклоняя NaN, бесконечность и значения вне диапазона. Значение задаёт DAC1/PA4; через внешний усилитель это приблизительно 0–10 В на вход тормоза. Команда удерживается без автоматического тайм-аута до следующей команды. Ноль возвращает выход в ноль.

`send_brake_5103` посылает ноль при штатных Ctrl+C и SIGTERM. При аварийном завершении процесса, потере связи или отключении компьютера контроллер не получит этот сброс и может продолжить удерживать последнее значение. Используйте ненулевую команду только после проверки механики и аварийного останова.

## Диагностика стенда

Проверить интерфейс и пассивно посмотреть трафик можно командами:

```bash
ip -details link show vcan2.0
candump vcan2.0
```

Если Heartbeat стенда виден, а `5100`/`5101` отсутствуют, прошивка могла не прочитать десятичный масштаб датчика. В serial CLI контроллера проверьте `status` и поле `decimal_point valid`. Если оно `no`, проверьте датчик, затем выполните `dyn stream start` и снова проверьте состояние и счётчики публикаций.

Скорость в проведённой ручной проверке оставалась неотрицательной при вращении в обе стороны, поэтому знак скорости не подтверждает направление вращения. Момент менял знак. Не рассчитывайте синхронные пары по близости сообщений `5100` и `5101`.

## Отличие от VBDRIVE

VBDRIVE — отдельное устройство на другой CAN-линии. Оно публикует `voltbro.foc.State.1.0` на subject `3811`; это не тип `Real32`, и данный пример на него не подписывается. `State` содержит время устройства, положение, скорость и момент, но не ток, напряжение и температуры. Эти величины читаются отдельными регистрами. После переноса мотора на `vcan1.0` проверьте его node ID.

Для установленной ранее прошивки VBDRIVE был известен баг повторного включения: запись `is_on=1` вскоре после `is_on=0` иногда не включала привод; пауза 10 секунд после подтверждённого выключения помогала в большинстве случаев. В последних прогонах оператор сообщил, что подтверждение `is_on=0` не приходило в течение 500 мс ожидания моторных примеров. Причина пока не установлена, а отправка команды не подтверждает фактического выключения. Перед следующей моторной пробой отдельно проверьте состояние привода. Моторные команды к `5103` и чтению DYN-200 отношения не имеют; в этом проекте для испытаний мотора оставлен отдельный заголовок [`vbdrive.hpp`](../include/voltbro_testbench_client/vbdrive.hpp).
